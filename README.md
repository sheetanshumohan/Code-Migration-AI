# Code Migration AI

Code Migration AI is a FastAPI + React application for AI-assisted legacy-code modernization. The repository contains a LangGraph workflow that analyzes a connected Git repository, builds an AST/dependency representation, creates an LLM-generated migration plan, pauses for operator approval, transforms selected files, generates tests, validates the workspace in a Docker runner when available, and produces a migration report plus a Git branch/PR delivery attempt.

> **Repository status:** This README is intentionally limited to behavior that is present in the current source tree. Features that exist only as configuration, comments, unused helper files, or future architecture are called out separately.

## What is implemented

The current repository implements these main pieces:

| Area | Current implementation |
|---|---|
| Backend | FastAPI application with REST APIs and WebSocket workflow streaming |
| Frontend | React 19 + Vite + Zustand SPA |
| Workflow orchestration | LangGraph with 7 agent node functions |
| Workflow approval | LangGraph `interrupt_after=["planner"]` in the Celery execution path (bypassable via `auto_approve`) |
| Repository ingestion | Git clone/sync + file listing + Tree-sitter parsing |
| Code intelligence | AST symbols, imports, call relationships, Neo4j graph |
| Migration planning | Pydantic structured plan generated by the configured LLM |
| Refactoring | LLM-generated complete-file transformations and unified diffs |
| Test generation | LLM-generated test files written into the repository |
| Validation | Docker execution when Docker is available; local subprocess fallback otherwise |
| Authentication | JWT access/refresh tokens, Argon2 password hashing, Google OAuth/Google ID-token login |
| Multi-tenancy | Organization/project/repository ownership checks in database queries |
| Git delivery | Git branch + commit + GitHub PR attempt when `GITHUB_TOKEN` is configured |
| Billing | Stripe checkout, confirmation and webhook endpoints |
| Observability | Prometheus, OpenTelemetry initialization, Sentry, structlog, LangSmith decorators |
| CI | Ruff, MyPy, Bandit, Pytest, Vitest and frontend build in GitHub Actions |

## Important limitations in the current code

The repository also contains partially wired or misleadingly named features. They should not be presented as fully operational capabilities:

1. **The validation retry counter is not incremented anywhere in the current workflow.** The routing function checks `retry_count`, but no node updates it, so the documented "maximum 3 reflection retries" behavior is not actually enforced.
2. **Migration validation is lighter than the CI validation.** The migration validator runs:
   - `npm test --if-present` for JavaScript/TypeScript repositories, and
   - `python -m py_compile ...` for Python repositories.
   The command strings end with `|| true`, and the `passed` flag is derived from detected `SyntaxError`/`TypeError` strings, not the subprocess exit code. It does not run the project's Ruff/MyPy/Bandit/Pytest suite as part of the migration workflow.
3. **The Docker sandbox has a local subprocess fallback.** It is therefore not guaranteed to be hermetic on every host.
4. **The Docker image defaults to `python:3.13-slim`.** JavaScript validation inside that image only succeeds when the image/environment actually contains the required Node tooling.
5. **Qdrant semantic search code exists, but repository indexing does not call `index_file_chunks()`.** The helper currently uses deterministic hash-based vectors rather than a model-produced embedding service. Search can therefore return no results unless vectors have already been inserted.
6. **Ollama is not implemented as a gateway class.** The active gateway factory implements OpenAI, Anthropic, Gemini, Groq and Perplexity.
7. **`dspy_optimizer.py` is an unused experimental module and DSPy is not listed in `backend/requirements.txt`.**
8. **Migration recipes exist in `backend/app/domain/migration/recipes.py`, but the current LangGraph refactor node does not invoke the recipe manager.**
9. **The Reviewer always persists a `PullRequest` record and can return a synthetic GitHub-looking URL when a real GitHub PR was not created.**
10. **Password reset is not sent by an email service in the current auth route.** `POST /auth/forgot-password` generates a short-lived reset token and returns it in the JSON response (and logs it), so the README should not claim SMTP/reset-email delivery.

## Workflow stages

The implementation has **7 LangGraph node functions**, while the UI tracks **6 main progress stages** because repository analysis and prompt validation share the first step index.

| Node | File | What the code actually does |
|---|---|---|
| `repo_analyst` | `backend/app/infrastructure/agents/nodes/repo_analyst.py` | Lists repository files, parses supported files with Tree-sitter, collects symbols/imports/calls and ingests the graph into Neo4j |
| `prompt_validator` | `backend/app/infrastructure/agents/nodes/prompt_validator.py` | For `custom_modernization`, validates that the custom objective is specific enough using a structured LLM response |
| `planner` | `backend/app/infrastructure/agents/nodes/planner.py` | Gets a Neo4j graph snapshot, filters candidate source files, asks the LLM for a structured task plan and falls back to deterministic batches when planning fails |
| `refactor` | `backend/app/infrastructure/agents/nodes/refactor.py` | Sends source files to the configured LLM, expects complete transformed file contents, creates unified diffs and writes transformed files |
| `test_generator` | `backend/app/infrastructure/agents/nodes/test_generator.py` | Generates a test file for each recently changed source file and writes it to the repository |
| `validator` | `backend/app/infrastructure/agents/nodes/validator.py` | Chooses a basic JS/Python validation command and executes it through the sandbox runner |
| `reviewer` | `backend/app/infrastructure/agents/nodes/reviewer.py` | Builds a Markdown migration report, creates a branch, commits changes, attempts a GitHub PR, and persists a `PullRequest` record |

### Actual LangGraph construction

The graph is built in `backend/app/infrastructure/agents/workflow.py`:

```python
workflow = StateGraph(MigrationWorkflowState)

workflow.add_node("repo_analyst", repo_analyst_node)
workflow.add_node("prompt_validator", prompt_validator_node)
workflow.add_node("planner", planner_node)
workflow.add_node("refactor", refactor_node)
workflow.add_node("test_generator", test_generator_node)
workflow.add_node("validator", validator_node)
workflow.add_node("reviewer", reviewer_node)

workflow.set_entry_point("repo_analyst")
workflow.add_edge("repo_analyst", "prompt_validator")
workflow.add_edge("prompt_validator", "planner")
workflow.add_edge("planner", "refactor")
workflow.add_edge("refactor", "test_generator")
workflow.add_edge("test_generator", "validator")
```

Validation is conditionally routed:

```python
workflow.add_conditional_edges(
    "validator",
    check_validation_results,
    {
        "check_next_task": "increment_task",
        "refactor_reflection": "refactor",
    },
)
```

The worker is what actually introduces the approval checkpoint:

```python
interrupt_nodes = [] if (is_resume or auto_approve) else ["planner"]

app_graph = build_migration_graph().compile(
    checkpointer=checkpointer,
    interrupt_after=interrupt_nodes,
)
```

## Repository intelligence

### Git engine

`backend/app/infrastructure/repository_intel/git_engine.py` provides:

- remote repository accessibility checks using `git ls-remote`
- authenticated Git cloning
- incremental `git pull` for an existing clone
- repository-local path isolation by organization and repository ID
- source-file listing with ignored directories/extensions
- path-traversal checks before file reads and writes
- language/framework heuristics
- repository deletion

### Tree-sitter support

The AST parser maps these file extensions:

| Extension | Parsed language |
|---|---|
| `.py` | Python |
| `.js`, `.jsx` | JavaScript |
| `.ts` | TypeScript |
| `.tsx` | TSX |
| `.java` | Java |
| `.go` | Go |
| `.rs` | Rust |
| `.cs` | C# |
| `.rb` | Ruby |
| `.php` | PHP |
| `.cpp` | C++ |
| `.c` | C |

The parser extracts:

- functions/methods
- classes
- imports
- call expressions
- start/end lines
- a simple cyclomatic-complexity estimate
- language and LOC metadata

It uses Tree-sitter first and has a regex fallback when the grammar/parser cannot be initialized.

### Neo4j graph

The graph stores:

```text
(:Repository)-[:CONTAINS]->(:File)
(:File)-[:DEFINES]->(:Symbol)
(:File)-[:IMPORTS]->(:File)
(:Symbol)-[:CALLS]->(:Symbol)
```

It also exposes a blast-radius query for callers of a symbol.

The React UI renders the file dependency graph with **React Flow + Dagre**.

## Semantic search

The repository contains a Qdrant search implementation in:

`backend/app/infrastructure/repository_intel/semantic_search.py`

The current embedding helper is deterministic and hash-based:

```python
def generate_deterministic_embedding(text: str, dim: int = 1536) -> list[float]:
    hasher = hashlib.sha256()
    hasher.update(text.encode("utf-8"))
    seed = int(hasher.hexdigest(), 16)

    vec = [math.sin(seed + i * 0.314159) for i in range(dim)]
    norm = math.sqrt(sum(x * x for x in vec)) or 1.0
    return [x / norm for x in vec]
```

Search is exposed through:

```http
GET /api/v1/search/{repo_id}?q=<query>&limit=<1..20>
```

The search route adds Redis caching around the Qdrant query.

**Important:** the current repository indexing task does not call `index_file_chunks()`, so automatic semantic indexing is not wired into the standard repository connection flow.

## Reports and PR delivery

The Reviewer node generates a Markdown report containing:

- workflow objective
- files modified
- number of generated tests
- validation result counts
- per-file explanations

It then:

1. creates or checks out a `codemigration/migration-<workflow-prefix>` branch
2. stages all repository changes
3. commits them
4. attempts to push with `GITHUB_TOKEN`
5. calls the GitHub Pull Request API when a GitHub remote and token are available
6. persists a `PullRequest` record

When the GitHub API cannot create the PR, the current code can still return a synthetic GitHub-style URL. That URL should not be treated as proof that a remote PR exists.

## Actual implementation snippets

### Starting a workflow

The public API accepts:

```python
class StartMigrationRequest(BaseModel):
    repository_id: str
    workflow_type: str = "framework_migration"
    source_framework: str | None = None
    target_framework: str = "Modern Architecture"
    target_language: str = "same_as_source"
    custom_goal: str | None = None
    auto_approve: bool = False
```

When `auto_approve` is true, the workflow automatically removes the planner interrupt and autonomously executes the entire migration plan without pausing for human interaction.

### Approval

The approval endpoint sets the relational workflow status and starts a resume task:

```python
wf.status = "executing"
await db.commit()

run_migration_workflow_task.delay(
    workflow_id=workflow_id,
    org_id=str(current_user.organization_id),
    repo_id=str(wf.repository_id),
    repo_path=repo_path,
    workflow_type=wf.workflow_type,
    target_framework=wf.target_framework,
    is_resume=True,
)
```

### File transformation

The refactor node expects the model to return the entire transformed file:

```python
response = await llm.generate_text(
    system_prompt,
    user_prompt,
    max_tokens=dyn_max_tokens,
)

transformed_code = response.content.strip()
```

It then creates a unified diff and writes the new file:

```python
diff_lines = list(
    difflib.unified_diff(
        original_code.splitlines(keepends=True),
        transformed_code.splitlines(keepends=True),
        fromfile=f"a/{rel_file}",
        tofile=f"b/{rel_file}",
    )
)

git_engine.write_file_content(
    state["repo_path"],
    rel_file,
    transformed_code,
)
```

### WebSocket event delivery

Workflow events are buffered in Redis and published through Redis Pub/Sub:

```python
history_key = f"workflow_events:{workflow_id}"
await redis.rpush(history_key, payload)
await redis.expire(history_key, 86400)

channel = f"ws:channel:workflow:{workflow_id}"
return await redis.publish(channel, payload)
```

### Sandbox command selection

The migration validator currently builds a simple command from repository contents:

```python
if has_js_ts:
    commands.append("node -v >/dev/null 2>&1 && npm test --if-present 2>&1 || true")

if has_python:
    commands.append(
        "python -m py_compile $(find . -name '*.py' -not -path '*/.*' 2>/dev/null) 2>&1 || true"
    )
```

That is the behavior that should be described in an interview or README—not a broader test/lint/type-check pipeline that the migration validator does not currently execute.

## Engineering Benchmarks

The project contains a comprehensive end-to-end benchmarking suite in the `benchmark/` directory. It evaluates:
- AST ingestion speed and limits (files processed per second)
- Agent reflection iterations and token consumption
- LLM API latency, timeouts, and costs
- Celery worker concurrency
- Database connection pool behavior under load

Live benchmarking outputs can be reviewed in:
- `benchmark_report.md`: Deep-dive engineering metrics and analysis.
- `resume_metrics.md`: Condensed stats suitable for CVs or executive summaries.
- `raw_metrics.json`: The complete underlying telemetry data.

These benchmarks are driven by the `comprehensive_live_benchmark.py` script, which launches realistic, multi-stage LangGraph workflows against an embedded test fixture repository.

## Security implementation

The source tree contains several concrete security controls:

- organization scoping for repository/workflow queries
- repository path traversal checks
- encrypted stored repository tokens
- Argon2id password hashing
- signed JWTs
- production secret validation
- rate-limit dependencies on sensitive API routes
- Stripe webhook signature verification
- prompt injection signature detection
- secret-redaction helpers
- WebSocket token validation when a token is supplied
- Docker sandbox restrictions: `--network=none`, capability dropping, no-new-privileges, PID/memory/CPU limits

These controls are implemented in code, but they should not be described as a complete enterprise security certification or guarantee.
